# ジャグラー設定推測ツール 基本設計書

**Version:** 0.1  
**Repository:** `keiyu-per/juggler-analyzer`

## 1. 目的

ジャグラー実戦中にiPhoneから数値を入力し、現在のボーナス確率・ブドウ確率・設定別の統計的な適合度を即座に確認できるツールを作る。

本ツール単体で基本的な設定推測を行えることを前提とし、ChatGPTは二次評価・補足分析に利用する。

## 2. 想定環境

- 主利用端末：iPhone
- UI：スマートフォン縦画面を優先
- 配布方式：GitHub Pages
- データ保存：ブラウザのLocalStorage
- 初期構成：HTML / CSS / JavaScriptを単一の `index.html` に格納
- サーバー側処理・AI APIは必須としない

## 3. 対応機種

v0.2では、実戦で遭遇する現行系ジャグラーを個別機種として登録する。

- マイジャグラーVI
- マイジャグラーV
- ネオアイムジャグラーEX
- アイムジャグラーEX（6号機）
- ファンキージャグラー2
- ハッピージャグラーV III
- ゴーゴージャグラー3
- ジャグラーガールズSS
- ミスタージャグラー
- ウルトラミラクルジャグラー
- その他

各登録機種は、北電子公式の設定別BB/RB確率を基準に設定別適合度を算出する。

「その他」は機種固有の設定別確率が不明なため、BIG/REG/合算/ブドウの観測値は表示するが、設定1〜6の適合度を推測しない。根拠のない汎用ジャグラー確率を当てはめることはしない。

ブドウ確率はメーカー非公表のため、設定別の十分な参考データを確認できた機種のみ補助材料として使用する。参考データが不足する機種でもカウント・表示は行うが、設定別適合度には加算しない。

機種別データの出典・採用方針は `docs/DATA_SOURCES.md` を基準とする。

## 5. 入力項目

### 現在データ

- 総回転数
- BIG回数
- REG回数
- 着席後累計ブドウ数（任意）

### 着席時データ

- 着席時総回転数
- 着席時BIG回数
- 着席時REG回数

着席時総回転数と累計ブドウ数が入力されている場合、

`着席後ゲーム数 = 現在総回転数 - 着席時総回転数`

としてブドウ確率を算出する。

## 6. 入力操作

実戦中の操作量を減らすことを優先する。

- 数値入力はiPhoneの数字キーボードを利用
- 機種を一覧から選択
- 入力後「評価を更新」で再計算
- 入力履歴は端末内に保存
- ブドウは画面左側の固定カウンターから1タップで加算可能
- 固定カウンターはスクロールしても画面内に残す
- 固定カウンターの中心位置は画面上端から約55%を基準とし、左端に固定する
- カウンター全体のサイズは初期v0.2実装比で約1.1倍とし、実戦中に押しやすいタップ領域を確保する
- 誤タップ訂正用に -1 操作も用意する
- カウンター値と「着席後 累計ブドウ」入力欄は常に同期する
- 新しい実戦開始時にはカウンターも0へリセットする
- 画面左上に固定の「GOGO!」ショートカットボタンを配置する
- GOGOボタン押下時は固定ブドウカウンターを一時的に非表示にする
- GOGOボタン押下時は現在の総回転数入力値をクリアする
- 総回転数をクリアした後、総回転数入力欄へ移動してフォーカスする
- GOGOボタン押下時は総回転数欄の直下にクイック入力を展開する
- BIG/REGのクイック入力完了時、またはクイック入力を閉じた時点で固定ブドウカウンターを再表示する
- クイック入力では「BIG +1」「REG +1」を選択できる
- 当選種別を押すと該当回数を1加算し、そのまま評価を更新する
- 総回転数が未入力の場合は加算せず、総回転数入力を促す
- GOGOボタンは実機のGOGOランプを想起させる、青い放射状ランプ背景＋ピンク系の「GOGO!」＋黄〜橙系の「CHANCE」表記とする
- 「CHANCE」はボタン全幅を基準に中央揃えする
- 「GOGO!」はボタン全幅ではなく青い放射状ランプ（ギザギザ）の幅を基準に中央配置する
- 「GOGO!」は斜体・回転による視覚的な左寄りを補正するため、ランプ幾何中心から約2px右へ補正する
- 縦方向は発光中心・GOGO!・CHANCEを一体で中央寄りに見えるよう調整し、上寄りに見えないことを基準とする
- 通常時は控えめな発光、押下時は約0.36秒だけ青いランプ・GOGO!・CHANCEの発光を強める
- 押下発光は入力ショートカット動作と同時に開始し、操作フィードバックとして利用する
- GOGOランプはパステル調ではなく、彩度の高いネオン質感を優先する
- 青い放射状ランプは中心白領域を小さくし、青〜濃紺のコントラストを主体とする
- 「GOGO!」は芯色をネオンピンクとして保持し、外周グローで発光感を作る
- 「CHANCE」は黄〜橙の芯色を保持し、橙〜赤橙の外周グローで発光感を作る
- 文字色そのものを白く淡くするのではなく、芯色＋外周発光でネオン感を表現する
- 承認済みの見た目確認用プレビューは `docs/review/gogo_neon_preview_20261007.svg` を基準資料として保持する

## 7. 基本計算

以下を表示する。

- BIG確率 = 総回転数 / BIG回数
- REG確率 = 総回転数 / REG回数
- 合算確率 = 総回転数 / (BIG + REG)
- ブドウ確率 = 着席後ゲーム数 / 着席後累計ブドウ数

表示形式は原則 `1/xxx.x` とする。

## 8. 現在値カード

BIG、REG、合算、ブドウを4つのカードで表示する。

実戦中に一目で確認できることを優先し、細かい説明より数値の視認性を重視する。

## 9. 総合評価

以下を表示する。

- 高設定寄り指数：0〜100
- 最も適合する設定
- サンプル充足度

### 高設定寄り指数

設定別適合度から得られる平均設定値を0〜100へ線形変換する。

`score = (平均設定 - 1) / 5 × 100`

これは勝率、期待収支、設定投入確率を意味しない。

## 10. 設定別適合度

設定1〜6について、観測データが各設定の理論値・参考値にどの程度整合するかを相対表示する。

重要：この値は「設定確率」とは呼ばない。

現行v0.1では設定ごとの事前確率を均等とみなした正規化尤度であり、ホールの設定配分などの現実的な事前分布は含まないため、「設定別適合度」と表現する。

## 11. 推測ロジック

主な評価材料：

- BIG
- REG
- ブドウ
- 総回転数（サンプル量）

BIG・REGは総回転数全体を利用する。

ブドウは着席後にユーザー自身が計測した範囲のみ利用する。

## 12. 統計計算

### BIG / REG

各設定について、

- BIG発生
- REG発生
- その他

の3カテゴリとして多項分布の対数尤度を計算する。

設定間比較では共通となる多項係数は省略可能。

### ブドウ

着席後ゲーム数を試行回数、ブドウ数を成功回数とする二項分布の対数尤度を利用する。

ブドウ値には解析・実戦上の参考値が含まれる可能性があるため、v0.1では重みを抑え、

`総合対数尤度 = ボーナス対数尤度 + 0.65 × ブドウ対数尤度`

とする。

### 正規化

設定1〜6の対数尤度をsoftmaxで正規化し、合計100%の設定別適合度として表示する。

## 13. サンプル充足度

v0.1では簡易指標として、

`min(総回転数 / 6000 × 100, 100)`

を利用する。

これは統計的な信頼区間そのものではなく、「現在どの程度ゲーム数が積み上がっているか」を直感的に示す補助指標。

## 14. 評価理由

BIG、REG、ブドウ、試行G数を個別に評価する。

表示例：

- かなり強い
- 良好
- 中間
- 弱め
- 未評価

最終スコアだけでなく、「何が評価を押し上げ／押し下げているか」をユーザーが確認できるようにする。

## 15. 前回入力との差分

将来的に前回評価時からの差分を表示する。

候補：

- 増加ゲーム数
- BIG増加数
- REG増加数
- ブドウ増加数
- スコア変化
- 最適合設定の変化

## 16. 推移表示

## 17. ChatGPT短縮コピー

ユーザーが従来使用している形式を維持する。

`総回転数,BIG,REG,着席後累計ブドウ`

例：

`5272,21,20,229`

## 18. ChatGPT共有テンプレート

ChatGPTへの共有は「何を確認したいか」を先に選び、目的別にプロンプトを切り替える。

初期テンプレート：

1. **設定再評価**
   - 生データを優先して独立に再評価
   - 強い材料・弱い材料
   - 試行数による不確実性
   - 自動判定とのズレ

2. **続行価値**
   - 現時点で続ける価値があるか
   - 続行 / 様子見 / 見切り寄り
   - 次の再判定ポイント

3. **やめ時**
   - 今やめるべきか、どこまで回すか
   - 残り時間・投資など追加状況を考慮
   - 具体的な終了条件を提示

4. **見切りライン**
   - どの数値・状況まで悪化したら見切るか
   - 次に確認するG数
   - REG・ブドウ・合算等の条件を具体化

5. **店舗・イベント込み信頼度**
   - 台単体の数値と店舗/イベント要因を分離して評価
   - イベント、島配置、周辺台等は補助材料として扱う
   - 店舗要因だけで設定を断定しない

6. **前回からの変化**
   - 直前評価から改善・悪化した材料
   - 判断が変わるほどの変化か
   - 追加サンプルで見るべき点

7. **着席価値**
   - 現在空いている台として座る価値
   - 現在データからの候補度
   - 追う場合の初期見切りライン

ChatGPT向けの文章は共通して以下を要求する。

- 結論を先頭に置く
- 原則8行程度までの簡潔な回答
- 入力数値を長く再掲しない
- 生データを優先し、ツールの自動判定を盲信しない
- 小サンプルでは断定しない
- 必要なら「次に何Gまで見るか」を具体的に示す

ChatGPT連携欄には「追加状況」入力欄を設ける。店舗・イベント、残り時間、投資額、持ちメダル、周辺台など、判断に必要な文脈を任意で追記できる。

短縮データコピー `総回転数,BIG,REG,着席後累計ブドウ` は従来通り残す。

## 19. ローカル履歴

同一実戦中の評価履歴をLocalStorageに保存する。

同一データの連続保存は避け、最大件数を制限する。

v0.1では最大50件。

## 22. 設計原則

1. 実戦中に素早く入力できること
2. AIがなくても基本判定できること
3. 判定根拠を確認できること
4. 小サンプルを過信させないこと
5. 「設定確率」と「適合度」を混同しないこと
6. ChatGPTへ生データを容易に渡せること
7. iPhone単体で運用できること
8. GitHubでバージョン管理し、GitHub Pagesへ継続的に反映できること

## 27. 開発・更新方針

- GitHubの `main` ブランチを公開版とする
- `index.html` がGitHub Pagesのエントリーポイント
- 仕様変更時は本設計書もコードと合わせて更新する
- 統計ロジック変更時は、変更理由と数式・基準値を明記する
- v0.2以降は単一HTMLへロジックを集約せず、責務ごとにファイルを分離する

基本構成：

```text
index.html
assets/
  css/
    app.css
  js/
    machines.js   # 機種別基準値・出典メタデータ
    analysis.js   # 尤度・適合度等の純粋計算
    storage.js    # LocalStorage
    prompts.js    # ChatGPT共有テンプレート
    app.js        # DOM操作・画面制御
```

統計計算・機種データ・表示制御・プロンプト生成を分離し、今後の機種追加やロジック修正時に `index.html` 全体を編集しなくて済む構造を維持する。

## 28. 変更管理

本プロジェクトは仕様駆動に加えて、変更要求（Change Request / CR）単位の変更管理を行う。

- 現在有効な仕様は本書 `docs/SPECIFICATION.md` を基準とする。
- 将来候補・未着手項目は `docs/BACKLOG.md` で管理する。
- 変更理由・変更前後・影響範囲・実施状況は `docs/CHANGELOG.md` で管理する。
- 主要な機能追加、仕様変更、不具合修正、統計ロジック変更、データ構造変更はCRを登録してから実施する。
- 実装により仕様が変わる場合、コード・仕様書・変更管理台帳の整合性を維持する。
- CR IDは `CR-YYYY-NNN` 形式とする。
