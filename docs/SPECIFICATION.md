# ジャグラー設定推測ツール 基本設計書

**Version:** 0.1  
**Repository:** `keiyu-per/juggler-analyzer`

## 1. 目的

ジャグラー実戦中にiPhoneから数値を入力し、現在のボーナス確率・ブドウ確率・設定別の統計的な適合度を即座に確認できるツールを作る。

本ツール単体で基本的な設定推測を行えることを前提とし、ChatGPTは二次評価・補足分析に利用する。

## 2. 想定環境

- 主利用端末：iPhone
- UI：スマートフォン縦画面を優先
- 配布方式：GitHub Pages
- データ保存：ブラウザのLocalStorage
- 初期構成：HTML / CSS / JavaScriptを単一の `index.html` に格納
- サーバー側処理・AI APIは必須としない

## 3. 対応機種

初期対応機種：

- マイジャグラーV
- ゴーゴージャグラー3
- SアイムジャグラーEX
- その他

「その他」では任意の機種名を入力できる。ただし設定別基準値を持たないため、基本確率のみ表示し、設定別適合度は算出しない。

将来的にファンキージャグラー、ハッピージャグラー等を追加する。

## 5. 入力項目

### 現在データ

- 総回転数
- BIG回数
- REG回数
- 着席後累計ブドウ数（任意）

### 着席時データ

- 着席時総回転数
- 着席時BIG回数
- 着席時REG回数

着席時総回転数と累計ブドウ数が入力されている場合、

`着席後ゲーム数 = 現在総回転数 - 着席時総回転数`

としてブドウ確率を算出する。

## 6. 入力操作

実戦中の操作量を減らすことを優先する。

- 数値入力はiPhoneの数字キーボードを利用
- 機種は大きな2×2ボタンから選択
- 入力後「評価を更新」で再計算
- 入力履歴は端末内に保存

## 7. 基本計算

以下を表示する。

- BIG確率 = 総回転数 / BIG回数
- REG確率 = 総回転数 / REG回数
- 合算確率 = 総回転数 / (BIG + REG)
- ブドウ確率 = 着席後ゲーム数 / 着席後累計ブドウ数

表示形式は原則 `1/xxx.x` とする。

## 8. 現在値カード

BIG、REG、合算、ブドウを4つのカードで表示する。

実戦中に一目で確認できることを優先し、細かい説明より数値の視認性を重視する。

## 9. 総合評価

以下を表示する。

- 高設定寄り指数：0〜100
- 最も適合する設定
- サンプル充足度

### 高設定寄り指数

設定別適合度から得られる平均設定値を0〜100へ線形変換する。

`score = (平均設定 - 1) / 5 × 100`

これは勝率、期待収支、設定投入確率を意味しない。

## 10. 設定別適合度

設定1〜6について、観測データが各設定の理論値・参考値にどの程度整合するかを相対表示する。

重要：この値は「設定確率」とは呼ばない。

現行v0.1では設定ごとの事前確率を均等とみなした正規化尤度であり、ホールの設定配分などの現実的な事前分布は含まないため、「設定別適合度」と表現する。

## 11. 推測ロジック

主な評価材料：

- BIG
- REG
- ブドウ
- 総回転数（サンプル量）

BIG・REGは総回転数全体を利用する。

ブドウは着席後にユーザー自身が計測した範囲のみ利用する。

## 12. 統計計算

### BIG / REG

各設定について、

- BIG発生
- REG発生
- その他

の3カテゴリとして多項分布の対数尤度を計算する。

設定間比較では共通となる多項係数は省略可能。

### ブドウ

着席後ゲーム数を試行回数、ブドウ数を成功回数とする二項分布の対数尤度を利用する。

ブドウ値には解析・実戦上の参考値が含まれる可能性があるため、v0.1では重みを抑え、

`総合対数尤度 = ボーナス対数尤度 + 0.65 × ブドウ対数尤度`

とする。

### 正規化

設定1〜6の対数尤度をsoftmaxで正規化し、合計100%の設定別適合度として表示する。

## 13. サンプル充足度

v0.1では簡易指標として、

`min(総回転数 / 6000 × 100, 100)`

を利用する。

これは統計的な信頼区間そのものではなく、「現在どの程度ゲーム数が積み上がっているか」を直感的に示す補助指標。

## 14. 評価理由

BIG、REG、ブドウ、試行G数を個別に評価する。

表示例：

- かなり強い
- 良好
- 中間
- 弱め
- 未評価

最終スコアだけでなく、「何が評価を押し上げ／押し下げているか」をユーザーが確認できるようにする。

## 15. 前回入力との差分

将来的に前回評価時からの差分を表示する。

候補：

- 増加ゲーム数
- BIG増加数
- REG増加数
- ブドウ増加数
- スコア変化
- 最適合設定の変化

## 16. 推移表示

将来機能として、実戦中の評価推移をグラフ化する。

候補：

- 高設定寄り指数
- REG確率
- ブドウ確率
- 設定別適合度

## 17. ChatGPT短縮コピー

ユーザーが従来使用している形式を維持する。

`総回転数,BIG,REG,着席後累計ブドウ`

例：

`5272,21,20,229`

## 18. ChatGPT詳細コピー

以下を整形してクリップボードへコピーする。

- 機種
- 現在総回転数
- BIG / REG
- BIG / REG / 合算確率
- 着席時データ
- 着席後ゲーム数
- ブドウ数・ブドウ確率
- 高設定寄り指数
- 最適合設定
- サンプル充足度
- 設定別適合度
- ChatGPTへの分析指示

ChatGPTにはツールの判定を盲目的に採用させず、生データから独立に再評価させる。

## 19. ローカル履歴

同一実戦中の評価履歴をLocalStorageに保存する。

同一データの連続保存は避け、最大件数を制限する。

v0.1では最大50件。

## 20. 新しい実戦

「新しい実戦を開始」操作で現在セッションの入力・履歴をリセットする。

誤操作防止のため確認ダイアログを表示する。

月別・店舗別・機種別集計も候補とする。

## 22. 設計原則

1. 実戦中に素早く入力できること
2. AIがなくても基本判定できること
3. 判定根拠を確認できること
4. 小サンプルを過信させないこと
5. 「設定確率」と「適合度」を混同しないこと
6. ChatGPTへ生データを容易に渡せること
7. iPhone単体で運用できること
8. GitHubでバージョン管理し、GitHub Pagesへ継続的に反映できること

## 25. 将来機能・バックログ

将来の機能追加・改善案は `docs/BACKLOG.md` で一元管理する。

バックログ項目は実装確定ではなく、実施を決定した時点で変更要求（CR）へ昇格させ、`docs/CHANGELOG.md` で正式な変更管理対象とする。

主な候補にはPWA対応、評価推移、前回入力との差分、収支管理、履歴管理、対応機種追加、複数台比較、ベイズ推定等がある。詳細・優先度・依存関係はBACKLOGを参照する。

## 26. データ構造

v0.1では主に以下をLocalStorageへ保存する。

- `ja_machine`：選択中の機種
- `ja_session`：現在の実戦セッションと評価履歴

将来、収支管理を実装する場合はセッションID単位で実戦記録を永続化する構造へ拡張する。

## 27. 開発・更新方針

- GitHubの `main` ブランチを公開版とする
- `index.html` がGitHub Pagesのエントリーポイント
- 仕様変更時は本設計書もコードと合わせて更新する
- 統計ロジック変更時は、変更理由と数式・基準値を明記する
- 将来的にファイル分割する場合も、iPhoneでの利用速度と保守性を優先する

## 28. 変更管理

本プロジェクトは仕様駆動に加えて、変更要求（Change Request / CR）単位の変更管理を行う。

- 現在有効な仕様は本書 `docs/SPECIFICATION.md` を基準とする。
- 将来候補・未着手項目は `docs/BACKLOG.md` で管理する。
- 変更理由・変更前後・影響範囲・実施状況は `docs/CHANGELOG.md` で管理する。
- 主要な機能追加、仕様変更、不具合修正、統計ロジック変更、データ構造変更はCRを登録してから実施する。
- 実装により仕様が変わる場合、コード・仕様書・変更管理台帳の整合性を維持する。
- CR IDは `CR-YYYY-NNN` 形式とする。
