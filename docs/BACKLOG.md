# 開発バックログ

**Project:** Juggler Analyzer  
**運用開始:** 2026-10-03

## 1. 位置づけ

本書は、将来実装する可能性がある機能・改善案を管理するバックログである。

- `SPECIFICATION.md`：現在有効な仕様
- `BACKLOG.md`：未着手・検討中の将来候補
- `CHANGELOG.md`：実施を決定した変更要求（CR）と変更履歴
- Git履歴：実際の実装変更

バックログ項目は、実施を決定した時点でCRへ昇格させる。CR化前の項目は「実装確定」を意味しない。

## 2. ステータス

| Status | 意味 |
|---|---|
| Candidate | 将来候補 |
| Reviewing | 要件・方式を検討中 |
| Ready | CR化できる程度まで整理済み |
| Promoted | CRへ昇格済み |
| Dropped | 採用しない |

## 3. 優先度

| Priority | 意味 |
|---|---|
| High | 近い段階で検討したい |
| Medium | 有用だが先行機能に依存する |
| Low | 長期候補・高度化 |

優先度は固定ではなく、実戦上の必要性や他機能との依存関係に応じて変更する。

## 5. 詳細

### BL-001 — PWA対応
- **目的:** ホーム画面から通常アプリに近い形で起動可能にする。
- **想定:** manifest、Service Worker等を導入する。
- **依存:** GitHub PagesのHTTPS配信。
- **CR化時の確認:** キャッシュ更新方式、オフライン利用範囲、バージョン更新時の挙動。

### BL-002 — ホーム画面用アイコン
- **目的:** iPhoneホーム画面上で識別しやすくする。
- **依存:** BL-001と同時実施を推奨。
- **CR化時の確認:** 192/512等の必要サイズ、iOS向け設定。

### BL-003 — 評価推移グラフ
- **目的:** 実戦中の高設定寄り指数等の変化を視覚化する。
- **候補:** 高設定寄り指数、REG確率、ブドウ確率、設定別適合度。
- **依存:** 現在のセッション履歴。
- **CR化時の確認:** グラフ対象、表示密度、履歴データ構造。

### BL-004 — 前回入力との差分
- **目的:** 直前の評価から何が変化したか即座に確認する。
- **候補:** 増加G、BIG増加、REG増加、ブドウ増加、スコア変化、最適合設定変化。
- **依存:** セッション履歴。

### BL-005 — 収支管理
- **目的:** 設定推測と実際の収支を同一ツールで管理する。
- **候補:** 日付、店舗、台番号、機種、投資、回収、差額、貯メダル、最終データ、メモ。
- **影響:** LocalStorageのデータモデル拡張が必要。
- **CR化時の確認:** 金額/枚数の扱い、セッションとの関連付け、既存データ移行。

### BL-006 — 履歴一覧・編集・削除
- **目的:** 保存済み実戦データを後から確認・訂正できるようにする。
- **影響:** 永続化方式とID設計。

### BL-007 — CSVエクスポート
- **目的:** 実戦・収支データを外部分析可能にする。
- **依存:** BL-005/006のデータモデル確定後が望ましい。

### BL-008 — 対応機種追加
- **Status:** Promoted
- **関連CR:** CR-2026-004
- **目的:** 現行系ジャグラーへ対応範囲を広げる。
- **対応方針:** BB/RBは北電子公式、ブドウは出典品質を分離して扱う。

### BL-009 — 店舗・台番号管理
- **目的:** 実戦記録を店舗・台単位で識別する。
- **依存:** BL-005との統合を推奨。

### BL-010 — 月次集計
- **目的:** 月単位の収支・実戦傾向を集計する。
- **依存:** BL-005、BL-009。

### BL-011 — 複数台比較
- **目的:** 候補台を同一画面で比較できるようにする。
- **CR化時の確認:** 比較指標、入力方式、同一機種/異機種比較の扱い。

### BL-012 — ベイズ推定
- **目的:** 店舗等の現実的な設定配分を事前分布として設定推測へ反映する。
- **注意:** 現行の「設定別適合度」と意味が変わるため、表示用語と統計設計を再検討する。
- **CR化時の確認:** 事前分布の根拠、更新方法、事後確率の表現、データ不足時の扱い。

## 6. CRへの昇格ルール

バックログ項目を実装すると決めた場合：

1. 要求・目的を確認する。
2. 影響範囲と依存関係を分析する。
3. `CR-YYYY-NNN` を採番して `CHANGELOG.md` へ登録する。
4. バックログのStatusを `Promoted` に変更し、関連CRを記載する。
5. 必要な仕様を `SPECIFICATION.md` へ反映する。
6. 実装・確認・コミットを行う。
7. CRを `Completed` にする。

この手順により「将来案」と「実施決定済み変更」を混同しない。
